# AFK 网络抑制与流量统计功能计划

## 问题与目标

为 DeerFolia 增加一个面向挂机场景的网络优化功能：当玩家被判定为 AFK 时，暂停向该玩家发送“非必要”的下行数据，以降低服务器流量与瞬时带宽；当玩家恢复活动时，自动恢复正常发送并补齐必要状态。同时增加统计能力，能够按玩家、按数据类型累计展示节约的总流量与峰值带宽。

## 当前代码状态

- 仓库已经有 DeerFolia 自定义配置体系，`DeerFoliaConfiguration` 通过 `DedicatedServer` 启动阶段加载，适合新增一个 `afk-network-optimization` 配置组。
- 现有“网络优化”仅覆盖 VarInt/帧编解码层（`0008-Network-Optimization.patch`），目标偏 CPU/编解码效率，还没有“按玩家抑制下行数据”的能力。
- 现有代码库没有现成的 AFK 检测、按玩家网络节流统计、或按数据包类别过滤发送的 DeerFolia 层实现。
- 当前工作树里未展开上游生成源码（例如 `ServerGamePacketListenerImpl`、`Connection`、`ServerPlayer` 等入口尚不可直接浏览），实现前需要先执行 `./gradlew applyAllPatches` 生成可编辑源码，再确认最终切入点。
- 当前 git 分支是 `ver/26.1.2`；最终交付需要落到 `dev/afk-optimize` 分支。

## 推荐实现方向

采用“广泛抑制 + 内部必需包直通 + 用户可配置的抑制分类白名单 + 恢复时重同步”的方式：

1. 新增 DeerFolia 配置，定义 AFK 功能开关、判定阈值、恢复同步策略、统计开关与采样粒度。
2. 在玩家连接/发送链路上挂接一个 AFK 发送策略层：
   - 维护每个玩家的活动状态；
   - 对出站数据按“内部必需直通类别”和“用户可见可抑制类别”分类；
   - AFK 时默认抑制所有非交互必需包，仅放行内部必需直通数据与用户显式加入白名单的可抑制类别；
   - 玩家恢复活动时触发一次安全的状态重同步。
3. 增加统计聚合器，记录：
   - 按玩家累计节约字节数；
   - 按可抑制数据类别累计节约字节数；
   - 总节约量与峰值节约带宽；
   - 通过命令提供查询出口用于观测。
4. 文档化配置与统计含义，并完成构建、离线模式联机、挂机模拟验证。

## 执行阶段

### 阶段 1：准备源码与确认切入点

- 创建并切换到 `dev/afk-optimize`。
- 执行 `./gradlew applyAllPatches`，展开上游源码。
- 定位最终修改入口，重点检查：
  - 玩家活动输入处理链（移动、转头、交互、聊天、命令等）；
  - 对单个玩家发送数据包的公共路径；
  - 区块、方块实体、实体跟踪、声音/粒子等高流量包的发送来源；
  - 将实际下行数据包映射到“必须直通 / 高价值可抑制 / 有条件抑制”三类；
  - 恢复活动后可复用的重同步入口（例如区块重发、实体重新跟踪、玩家状态补发）。

### 阶段 2：AFK 状态与配置

- 在 `DeerFoliaConfiguration` 增加新的配置组，建议包含：
  - `enabled`
  - `afk-threshold-ticks`
  - `count-look-changes-as-activity`
  - `resync-on-resume`
  - `stats-enabled`
  - `suppression-whitelist-categories`
  - `max-suppressed-bytes-before-category-resync`（可选，支持无限制）
- 其中“仅转头/移动视角是否算恢复活动”按你的要求做成配置项，不硬编码。
- 新增 DeerFolia 自有类，集中管理：
  - 玩家最近活动时间
  - 当前 AFK/活跃状态
  - 状态切换回调
  - 每个玩家、每个可抑制类别的已抑制字节累计

### 阶段 3：用户可见的可抑制数据分类

- 面向统计和配置，只暴露“可抑制类别”，不把内部必需直通类别暴露给用户。
- 推荐把可抑制数据整理成以下用户可理解、可配置的类别：
  - **chunk-stream**
    - 区块数据、光照、区块卸载/重载、批量区块相关同步
    - 这是挂机场景下最可能占据大头带宽的类别之一
  - **block-updates**
    - 单方块更新、批量方块更新、方块实体数据、与世界方块状态变化直接相关的同步
    - 对生电装置、红石、容器、漏斗、机器附近场景尤为关键
  - **entity-stream**
    - 实体生成/销毁、移动、传送、朝向、元数据、属性、装备、乘客、牵引、动画等实体跟踪流
    - 对挂机刷怪塔、堆积实体、掉落物场景的带宽影响通常很大
  - **world-effects**
    - 粒子、声音、游戏事件、关卡事件、提示性视觉/环境反馈
    - 节流风险较低，用户也更容易理解
  - **ui-stream**
    - 计分板、队伍、TabList、BossBar、Title/Subtitle/ActionBar、Toast、地图、进度提示等展示类同步
    - 通常不是最高流量来源，但适合做成可选白名单项，避免和依赖 UI 提示的插件冲突
- 统计展示与配置白名单都围绕这些类别展开；实现时再把具体数据包映射到上述类别。

### 阶段 4：出站数据分类与抑制

- 在公共发送路径增加分类与统计钩子，优先避免在许多零散调用点重复逻辑。
- 第一版实现上保留内部“必需直通”集合，但不把它作为配置或统计维度暴露给用户。
- 对 `chunk-stream`、`block-updates`、`entity-stream`、`world-effects`、`ui-stream` 建立明确枚举或分类器，避免后续补丁里散落 `instanceof` 判断。
- 用户可以通过 `suppression-whitelist-categories` 指定某些类别不抑制，例如只保留 `ui-stream` 或 `world-effects`。
- 为每个被抑制的数据包记录节约字节数，并累计到玩家与类别维度。

### 阶段 5：恢复活动后的安全重同步与最大抑制上限

- 当玩家从 AFK 切回活跃时：
  - 解除抑制；
  - 主动触发一次世界与实体状态补齐；
  - 防止玩家看到过期世界快照或缺失实体。
- 增加一个可选的“最大抑制”配置：
  - 以“单玩家、单类别累计已抑制字节数”为阈值；
  - 当某类别对某玩家的累计抑制超过阈值时，提前做一次该类别对应的局部同步，避免恢复活动瞬间集中补发造成客户端尖峰压力；
  - 允许配置为无限制抑制，即只在玩家恢复活动时统一补同步。
- 若公共重同步接口不足，再补一个 DeerFolia 层协调器，集中处理恢复动作。

### 阶段 6：统计输出与观测

- 设计统计数据结构，至少输出：
  - 总节约流量
  - 分玩家节约流量
  - 分可抑制类别节约流量
  - 峰值节约带宽（需要定义时间窗口）
- 统计结果通过命令查询提供，例如 DeerFolia 管理命令下的子命令；实现前根据上游实际命令注册方式确认是直接接入 Brigadier 还是复用现有服务器命令模式。
- 若实现成本低，可额外接入 bStats 自定义图表做全局概览，但不是本次主验收项。

### 阶段 7：构建与验收

- 重新生成补丁：`./gradlew rebuildAllServerPatches`
- 构建打包：`./gradlew createPaperclipJar`
- 在 `/workspaces/runtime` 进行集成验证：
  - 以离线模式启动服务器；
  - 使用无头 Minecraft 客户端以离线模式接入；
  - 模拟 AFK 与恢复活动；
  - 验证日志、统计输出、流量节约和恢复同步行为；
  - 确认服务端不报错。

## 风险与关键点

- “非必要数据”范围已经确定为广泛抑制，这会显著提高客户端状态陈旧或漏同步的风险；实现上必须采用明确的内部直通集合，并在恢复活动后做强制重同步。
- Folia/Paper 的发送路径可能分散在多个上游类中；应先找公共发送钩子，无法统一拦截时再退而求其次在高流量发送源头分层处理。
- 统计峰值带宽必须先定义时间窗口，否则“峰值”不可比较。
- “最大抑制后局部同步”能降低恢复活动瞬间的客户端压力，但会增加实现复杂度，因为需要为不同类别设计对应的局部补同步策略。
- 无头客户端测试工具可能需要在 `/workspaces/runtime` 临时下载或构建。

## 已确认决策

- AFK 状态下采用“广泛抑制所有非交互必需包；内部必需直通集合始终放行，用户白名单仅作用于可抑制类别”的策略。
- “仅转头/移动视角是否算恢复活动”做成配置项。
- 统计结果通过命令查询，不以周期性日志作为主出口。
- 用户可见的统计与配置白名单只围绕可抑制类别展开，不暴露内部必需直通类别。
